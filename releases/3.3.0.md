# PlexonUtility 3.3.0

PlexonUtility 3.3.0 expands the stable Core-native Utility hub with a compact native administrative control plane while preserving the existing AFK runtime, quiet-feedback model, PlexonFamily integration boundaries, and performance model.

## Highlights

- dedicated 45-slot Admin Center with paginated online-player selection and focused per-player actions
- read-only `/invsee <player>` with cloned storage/armor/offhand presentation and safe target-disconnect handling
- event-driven native `/vanish [on|off]` with granular visibility permission, tab-list reconciliation, optional persistence, and join/quit suppression
- native Adventure `/kick`
- native profile `/ban` and `/unban` using Paper/Bukkit ban authority rather than a private moderation database
- permanent and bounded temporary bans with validated `m`/`h`/`d` duration syntax
- `/prison status|set|goto|send|clear` as a single holding waypoint, not a sentence/jail engine
- Paper Dialog typed moderation input followed by explicit Core GUI confirmation
- granular admin permission model and server-log audit records
- `admin-data.yml` for minimal Utility-owned runtime state only
- `%plexonutility_vanished%` and binary-compatible `PlexonUtilityAPI#isVanished(UUID)`
- consistent non-italic menu naming/lore and safe runtime value insertion

## Safety and performance

- no admin polling task, per-player repeating task, inventory polling, vanish scan, prison scan, or integration poll
- no synchronous network profile lookup on the primary thread
- admin persistence writes only on state changes through PlexonCore's IO scheduler lane
- inventory inspection is read-only; editable invsee was deliberately deferred rather than shipping an unsafe mirrored inventory
- no IP bans, mute, freeze, punishment-history DB, appeals, web panel, cross-server moderation, rank/economy editor, inventory rollback, or nickname management

## Migration notes

This release intentionally supersedes the older repository decision that all vanish/moderation capabilities remain external, but only for the narrowly documented native feature set.

If SuperVanish or another vanish provider is currently authoritative, do not intentionally run both engines as authorities. Choose one provider during cutover. TAB rules that depended on `%supervanish_isvanished%` should migrate to `%plexonutility_vanished%` or a direct native-compatible condition. PlexonChats join/quit hiding should be validated with its hidden-message/respect-hidden behavior.

PlexonHomes, PlexonTravel, PlexonBlacksmith, PlexonRanks/LuckPerms, PlexonJobs, PlexonChats, economy/shop providers, and claims/flags providers keep their existing ownership.
